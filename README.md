# CS465-FullStack-SNHU-C-1
CS-465 Full Stack Development with Mean
The Travlr getaways were definitely a challenging project for me to work on. Frontend development was something I knew would be challenging; however, I did have to adjust my thought processing throughout the development of the project. Working on static HTML through Express seemed simple and felt straightforward. Having the server render the page and sending it to the browser was very simple and very functional. It works, but it will be limited in terms of navigation and will require a full page to reload as well when navigating. Moving into JavaScript with templating made me think and work more dynamically since the trip data was being pulled from the backend through MongoDB and was therefore passed into the page before rendering, which does solve hardcoding content. The biggest change was building the Angular Single Page application for the admin side. The SPA loading once and then communicating with the backend through REST API calls, and then receiving JSON and updating only what needed to change, was a lot of work, but I eventually managed to figure it out after my debugging, as my versions were more updated. This does mean that the Travlr Getaways was more modern but also more complex. The newer Angular version honestly is what led me to having the most issues, as some of the course examples couldn't directly apply. This forced me to look into what Angular was actually doing, which means that I can't just copy the syntax. 

The backend of MongoDB was great. I've previously worked with MongoDB for a Shelter-based project for another course, and within a MEAN stack, it functioned properly. MongoDB stores data as JSON documents with helps align with JavaScript running on both sides of the application. Instead of translating relational tables into JavaScript objects, everything is the same language in a sense, and therefore functions a little bit more easily. Using Mongoose also added structure as well as flexibility by allowing schemas and validation rules for trip data. The travel application may be upgraded in the future or add new data fields, and these can change or evolve, and a document-based database allows for great flexibility without sacrificing organization. This is like a puzzle, fits perfectly into the architecture instead of fighting against it. 

The most important concept I understand the best is the difference between JavaScript and JSON. JavaScript is a programming language and handles our logic, behavior, and execution. JSON is just a data format and has no functions or behavior its data that's structured. Having JSON means that our data is organized properly, and having an Angular frontend means that HTTP requests are sent, Express retrieves said data from MongoDB, this is then serialized or written or retrieved from JSON, and then is sent back. Angular translates JSON into proper usable JavaScript objects and is then rendered into the UI. This loop relies entirely on JSON as the glue. Understanding this pipeline made the full stack much more comprehensive and easier to implement. 

Throughout development, I refactored code multiple times, and I centralized API calls into a dedicated Angular service instead of letting each component make its own HTTP request. Once we introduced JWT authentication, I just needed to update this service and its interceptor rather than rewrite all of my components. I also focused on easy, reusable UI components for the trip cards and shared layout elements. The benefits were great: less duplicated logic, easier debugging, cleaner structure, and overall better scalability. 

Testing also became more layered once security was introduced. Understanding HTTP methods and endpoints is crucial. GET retrieves data, POST creates or authenticates, PUT updates, and DELETE removes. This is very similar to CRUD operations, and each endpoint maps to a specific operation. Using Postman made all of my testing and debugging so much easier. I was able to isolate and test API routes before connecting Angular, and this helped me identify whether issues came from routing, controllers, or the database itself. When JWT authentication was added, testing did require an additional step to obtain a token through login, then include that token in the Authorization header for protected routes. Being able to verify that unauthorized requests got a 401 error was also just as important as confirming that valid requests succeeded. This process greatly reinforced how backend security functions and will function in a real-world application. 

Overall, this course definitely showed me some of my weaknesses, and Ive learned alot and this goes beyond understanding concepts but actually being able to build a secure full-stack application from start to finish on my own. I now know the RESTful API structure, MongoDB integration, Angular SPA development, and JWT authentication at an implementation level. I also now know what to expect in terms of better problem-solving habits. I already solve problems in terms of diagnostics at work and have a very structured thought process, but when it comes to documentation, that doesn't perfectly match the framework version I was using. Instead of stopping when something broke, I pushed through the version differences and architectural adjustments and adapted, debugged, and, in all honesty, this is the reason why I'll be more confident moving forward, as I pushed through those issues.
